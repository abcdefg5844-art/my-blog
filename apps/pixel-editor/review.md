# 픽셀 아트 에디터 Review

## 요약
- 결과: **통과** (3차 수정 후 재검증: 문제 6 해결, 기록 한도 100 유지. 2차·1차 수정과 그리기·되돌리기·자동 저장·복원·PNG 회귀 없음. 단, 되돌리기 동작에 관해 낮음 1건(문제 7)을 새로 기록했다 — 두 창에서 번갈아 되돌리면 서로의 되돌리기를 취소하며 같은 두 상태를 오가고, 합친 창의 첫 되돌리기는 다른 창의 획을 지운다. 두 창을 함께 쓸 때만 생기며 데이터는 되돌리기/다시 실행으로 복구된다 — 아래 "재검증 (3차 수정 후)")
- 2차 수정 후 재검증 결과: 통과 (문제 4·5 해결, 새로 낮음 1건(문제 6) 발견)
- 1차 수정 후 재검증 결과: 통과 (지적한 낮음 3건 해결, 새로 낮음 2건(문제 4·5) 발견)
- 로직 테스트: **53/53 통과** (`test.html`, 실패 항목 없음, 콘솔 오류 없음 — 1차·2차·3차 재검증 때도 동일)
- 최초 검증 결과: 통과 (높음·중간 없음, 낮음 3건)
- 확인 방법: 내장 브라우저(`mcp__Claude_Browser__*`)로 `http://localhost:8000/apps/pixel-editor/`, `test.html`, 블로그 메인(`/`)을 실제로 열어 확인했다.
  - 실제 입력: PNG 저장 버튼 실제 클릭(ref 클릭), 배율 `<select>` 값 변경, 실제 키 입력(Tab 30회, 방향키, Space/Enter, Shift+방향키, Home/End, `b`/`e`/`f`/`g`, Ctrl+Z, Ctrl+Shift+Z, Ctrl+Y), 블로그 테마 버튼 실제 클릭.
  - 합성 이벤트: 보드 그리기(마우스·터치 `PointerEvent`), 한글 자판 상태(`key: 'ㄷ'`, `code: 'KeyE'` 등 `KeyboardEvent`), `contextmenu`. 창이 숨겨져 스크린샷이 계속 시간 초과되어 좌표 클릭은 쓸 수 없었다. 레이아웃은 `getBoundingClientRect`·`scrollWidth`로 쟀다.
  - 숨겨진 창에서는 `requestAnimationFrame`이 멈춰 보드 DOM 갱신이 늦게 반영되는 경우가 있었다. 그래서 그림 상태는 자동 저장된 `localStorage['pixel-editor-state']`(300ms 뒤)와 버튼 상태로 확인했다. 새로고침 뒤에는 DOM 칸 색을 저장값과 256칸 모두 비교했다.
  - PNG: 페이지에서 `URL.createObjectURL`과 `HTMLAnchorElement.prototype.click`을 임시로 감싸 실제 저장 동작이 만든 Blob을 가로챘다. 원래 `click`은 호출하지 않아 **디스크에 파일을 남기지 않았다**. Blob을 `Image`/`createImageBitmap`으로 다시 읽어 캔버스 `getImageData`로 픽셀을 확인했다.
  - 정리: `localStorage`를 검증 전 상태(키 없음, `pixel-editor-state`·`theme` 모두 없음)로 되돌렸다. 화면 크기 에뮬레이션은 `preset: "desktop"`으로 되돌렸다. colorScheme은 바꾸지 않았다. 블로그에 임시로 넣은 iframe은 제거했고 파일은 만들지 않았다.

## Build가 보고한 spec과 다른 점에 대한 판단
| 차이 | 판단 |
|---|---|
| 데스크톱 카드 보드 약 414px | 타당. 634px 폭에서 여백 24 + 간격 16 + 패널 최소 180을 빼면 414가 최대다. spec의 "약 480px"는 이 폭에서 불가능한 추정치였다. 700×520에서는 475px |
| `createHistory`가 `limit` 포함 반환 | 타당. `{ past, future }`에 필드 하나가 더 붙을 뿐이고 테스트·사용처에 영향 없음 |
| 배율 표기 축약(`1×` 등) | 타당. 저장 뒤 알림에 실제 크기(예: 256×256)가 나오므로 정보 손실이 작다 |

## 발견한 문제

### [심각도: 낮음] 1. 채우기 도구에서는 두 번째 손가락(다른 포인터)이 무시되지 않음
- 재현 방법: 채우기 도구 선택 → 한 손가락으로 보드를 누른 채(`pointerdown`, id 31) 다른 색을 고르고 두 번째 손가락으로 보드를 누른다(`pointerdown`, id 32). 두 손가락으로 확대하려는 동작에서도 같은 일이 생긴다.
- 기대 동작: spec 3장 "두 번째 손가락 등 다른 포인터는 무시".
- 실제 동작: 채우기는 `pointerdown`에서 바로 실행하고 `stroke`를 만들지 않아 활성 포인터가 기록되지 않는다. 그래서 두 번째 포인터도 채우기를 한 번 더 실행하고 되돌리기 기록이 2단계 생긴다(합성 터치 이벤트로 확인: 파랑 166칸 + 초록 63칸). 펜·지우개는 정상적으로 무시된다.
- 관련 위치: `apps/pixel-editor/main.js:480-501`

### [심각도: 낮음] 2. 사용자 색이 선택된 상태가 화면 낭독기에 전달되지 않음
- 재현 방법: 사용자 색을 고른 뒤 Tab으로 사용자 색 입력에 이동한다.
- 기대 동작: 팔레트 칸의 `aria-pressed`처럼 "선택됨" 상태를 알 수 있다.
- 실제 동작: aria-label은 "사용자 색 고르기, 현재 #123abc"로 같고 선택 여부는 링·체크(시각)로만 표시된다. 예를 들어 선택 중일 때 aria-label 끝에 ", 선택됨"을 붙이면 해결된다. 색을 바꿀 때 live region에 "#123abc 선택, 펜"이 나오므로 영향은 작다.

### 3. 코드 리뷰: `basePixels` 합치기의 경계 상황
| 상황 | 판단 | 근거 |
|---|---|---|
| 전체 지우기와 동시 변경 | 동작 정상 | A 전체 지우기 → 50ms 뒤 B 0행 초록 획 → 양쪽·저장값 모두 "지운 그림 + B의 0행"(16칸), 저장 A 1회·B 1회. 반대로 B가 지우고 A가 그리면 지운 그림 위에 A 획이 남는 구조(코드). 다만 A의 되돌리기 기록이 비워져 전체 지우기를 되돌릴 수 없게 된다(문제 6) |

### 4. 새로 발견한 문제

#### [심각도: 낮음] 6. 다른 창이 저장하면(설정만 바꿔도) 이 창의 되돌리기 기록이 모두 지워짐
- 재현 방법: B에서 획 두 개를 그린다(되돌리기 활성). A에서 그림은 건드리지 않고 격자선·색·도구만 바꾼다.
- 기대 동작: 그림이 바뀌지 않았으면 B의 되돌리기 기록은 그대로다. 그림이 바뀌었더라도, 특히 전체 지우기 직후에는 "되돌리기로 복구할 수 있습니다"라는 안내대로 복구할 수 있어야 한다.
- 실제 동작: A의 설정 저장을 받은 B에서 되돌리기·다시 실행이 모두 비활성이 됐다. `applyRemote`가 그림 변화와 관계없이 기록을 새로 만든다(`main.js:767`). 같은 이유로, 한 창에서 전체 지우기를 한 뒤 다른 창이 무엇이든 저장하면(색 하나만 골라도) 지운 창에서 되돌리기로 복구할 수 없다. 전체 지우기 + 50ms 뒤 다른 창 획 시험에서도 A의 되돌리기가 비활성이었다. 두 창을 함께 열어 둘 때만 생긴다. 예를 들어 `!pictureChanged && !localChanged`면 기록을 유지하고, 그림이 바뀐 경우에는 기존 기록 위에 받은 그림을 새 단계로 쌓으면 해결된다.
- 관련 위치: `apps/pixel-editor/main.js:762-771`

### 정리 (2차)
- `localStorage`를 검증 전 상태(키 없음, `pixel-editor-state`·`theme` 모두 없음)로 되돌렸다. 임시 iframe 두 개는 제거했다. 블로그의 원래 카드 iframe(`apps/2048/`, `apps/pixel-editor/`)은 건드리지 않았다.
- 화면 크기 에뮬레이션을 `preset: "desktop"`으로 되돌렸다. colorScheme은 바꾸지 않았다.

### 3. 코드 리뷰: 다른 창 값을 받은 뒤 되돌리기 → 저장·전파
- 저장 폭주나 무한 반복은 없다. 되돌리기를 한 창만 저장하고, 받은 창은 `localChanged`가 없어 저장하지 않는다(시험에서 추가 저장 0회). 받을 때마다 받은 창의 기록이 한 단계씩 늘지만 한도 100에서 멈춘다.
- 다만 "다른 창에서 받은 그림"도 이 창의 한 단계가 되면서, 두 창의 되돌리기가 서로 얽힌다(문제 7).

### 4. 새로 발견한 문제

#### [심각도: 낮음] 7. 다른 창에서 받은 변경이 이 창의 되돌리기 단계가 되어 두 창의 되돌리기가 서로를 취소함
- 재현 방법 1(번갈아 되돌리기): A 1행 → B 2행 → A 3행을 차례로 그려 저장값 1·2·3행. A에서 되돌리기, B에서 되돌리기를 번갈아 6번 누른다.
- 재현 방법 2(합친 창의 되돌리기): A 7행 획 → 50ms 뒤 B 9행 획(B가 합침). B에서 되돌리기 한 번.
- 기대 동작: 각 창의 되돌리기는 대체로 그 창에서 한 동작을 거슬러 간다. 번갈아 누르면 기록을 계속 거슬러 가고, 합친 창의 첫 되돌리기는 그 창의 획(9행)을 취소한다(2차 재검증에서 확인했던 동작).
- 실제 동작:
  - 방법 1: 저장값이 1·2 → 1·2·3 → 1·2 → 1·2·3 …으로 같은 두 상태만 오간다. B의 되돌리기는 "A의 되돌리기를 받은 단계"를 취소해 3행을 되살리고, 그 저장을 받은 A는 새 단계가 쌓이면서 다시 실행 목록이 비워진다(A 다시 실행이 활성 → 비활성). 그래서 두 창을 번갈아 써서는 더 이전 그림으로 돌아갈 수 없다.
  - 방법 2: B의 첫 되돌리기는 받은 단계를 취소해 **A의 7행**을 지우고, 이 결과가 저장되어 A 화면에서도 7행이 사라진다(양쪽 9행만). 두 번째 되돌리기에서야 B의 9행이 취소된다.
  - 데이터가 영구히 사라지지는 않는다. 다시 실행이나 다른 창의 되돌리기로 돌아온다. 두 창을 함께 열고 번갈아 되돌릴 때만 생긴다. "되돌리기는 받기 전 그림으로"라는 3차 설계의 결과이기도 하다.
- 제안(선택): 받은 단계는 기록에 쌓되, 되돌리기는 이 창이 직접 만든 단계만 거슬러 가게 한다(예: 기록 항목에 `remote` 표시를 두고 되돌리기 때 받은 단계는 그 위의 이 창 변경만 빼는 방식). 또는 현재 동작을 의도된 것으로 받아들이고 그대로 둔다. 한 창만 쓰는 일반적인 경우와 문제 6(지우기 복구)에는 영향이 없다.
- 관련 위치: `apps/pixel-editor/main.js:766-772`, `apps/pixel-editor/main.js:775-780`

## 기타 의견
- 코드 리뷰에서 포인터 상태가 꼬일 경로는 찾지 못했다. `pointerup`과 `lostpointercapture`가 모두 와도 `endStroke`가 `stroke`를 먼저 비우므로 기록이 한 번만 남는다. 획 중에는 되돌리기·단축키·키보드 그리기가 막혀 있다. 리스너는 모듈 최상위에서 한 번만 등록한다.
- 되돌리기 기록: `commit`은 그림이 바뀐 경우에만 push한다(같은 색 칠하기·채우기는 기록 없음). 실제로 확인한 결과와 같다.
- 자동 저장: 300ms 디바운스 하나만 쓰고, 실패는 try/catch로 무시하며, `deserialize`는 칸 값·현재 색·도구·격자선을 모두 검증한다. 저장값이 DOM에 들어가는 곳은 `style.backgroundColor`뿐인데, 검증된 `#rrggbb`만 들어간다.
- 보드 밖으로 끌고 나가면 가장자리 칸이 칠해지는 것은 spec 3장의 "0~15로 자름"을 그대로 따른 결과다. 의도와 다르면 spec에서 다시 정하면 된다.
- 아주 좁은 폭(≤340px, 모바일 카드 iframe)에서는 팔레트 칸이 26px로 spec의 28~32px보다 조금 작다. WCAG 2.5.8 최소 24px은 충족한다.
- 라이트 테마의 보드 테두리(`--board-frame` `#c9ced6`)는 배경 대비 1.58로 약하지만, 체크무늬와 격자선이 있어 보드 영역은 구분된다.
- 미확인 항목(실기기 터치 스크롤 방지, 실제 coalesced 이벤트, 실제 파일 다운로드, 실제 색 고르기 창, OS 테마 실시간 전환, reduced-motion 실제 표시)은 실제 휴대폰과 OS 설정으로 사람이 한 번 확인하기를 권한다.
